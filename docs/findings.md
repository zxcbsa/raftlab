# 真机联调发现的问题复盘

首次在 Linux 上跑通时暴露的 10 个问题。前 5 个属于测试框架，后 5 个是被测系统本身的缺陷——这也说明黑盒压测确实能逼出代码里的问题。

## 汇总

| # | 问题 | 归属 | 严重度 |
|---|---|---|---|
| 1 | 仓库自带 pb 由旧版 protoc 生成，编译失败 | 构建 | 阻塞 |
| 2 | `kvstatus` stdout 混入日志，telemetry 解析崩溃 | 工具 | 高 |
| 3 | chaos 与 orchestrator 各持一个 EventLog，事件被覆盖 | 工具 | 高 |
| 4 | `maxRaftState` 写死在 `raftKvDB`，场景配置无效 | 系统 | 中 |
| 5 | 跳表逐操作 `cout`，6 秒 25MB 日志 | 系统 | 高 |
| 6 | `MprpcChannel` 非线程安全，并发调用读串响应 | 系统 | 高 |
| 7 | 选举期间客户端高频重试，饿死选举 | 系统/工具 | 高 |
| 8 | per-node 端口 >32767，`short` 溢出成负数 | 工具 | 中 |
| 9 | Raft 未 init 就收 RPC → 空指针段错误 | 系统 | 致命 |
| 10 | `availability` 把 restart 的 inject 算进故障窗口 | 工具 | 低 |

## 详述

### 1. protoc 版本不匹配

**现象**：`#error This file was generated by an older version of protoc`，随后 `generated_message_table_driven.h: No such file`。

**原因**：仓库提交的 `*.pb.h/.cc` 是 protobuf 3.6 时代生成的，系统是 3.21。

**处理**：用与运行时同版本的 protoc 重新生成 4 个 proto；`rpcheader.pb.cc` 在仓库里被重命名为 `.pb.cpp`，重生成后要同步改名。

### 2. telemetry 采样为 0

**现象**：`raftlab telemetry` 输出 `samples=0`，没有 `metrics.jsonl`。

**原因**：`kvstatus` 内部的 `MprpcChannel` 会 `DPrintf` 到 stdout，`json.loads` 在日志行上抛 `JSONDecodeError`，采样线程静默退出。

**处理**：只解析以 `{` 开头的行；采样异常不再终止线程，而是写 `sampled:false`。

### 3. 事件被覆盖

**现象**：`availability.maxGapMs` 恒为 0，`events.json` 里没有 `fault.inject`。

**原因**：`Chaos` 自己 new 了一个 `EventLog`（读文件 → 内存列表），orchestrator 结束时用自己的旧列表 `save()`，把 chaos 写的事件整个覆盖。

**处理**：orchestrator 把自己的 `EventLog` 传给 `Chaos`，全流程共享一个实例。

### 4. 快照阈值不可配

**现象**：场景里写 `maxRaftState: 50000` 但行为没变，每次写都做全量快照，吞吐只有 80 ops/s。

**原因**：`raftKvDB.cpp` 里 `new KvServer(i, 500, ...)` 写死。而 `IfNeedToSendSnapShotCommand` 的判断是 `> maxRaftState/10`，500 意味着 **50 字节**就快照。

**处理**：新增 `-m` 参数，Cluster 透传并记录到 `cluster.json`；场景默认改为 50000。

### 5. 日志成为瓶颈

**现象**：6 秒压测产生 25MB `cluster.log`。

**原因**：`SkipList::insert_element/search_element` 每操作 `std::cout`，与 `DPrintf` 无关，关掉 `Debug` 也还在。

**处理**：`SKIPLIST_LOG` 宏受 `RAFT_DEBUG_LOG` 控制；日志降到 250KB。

### 6. 同一个 channel 并发调用

**现象**：杀 leader 后剩余节点长时间选不出主，日志里大量 `not leader`。

**原因**：Raft 的心跳线程与选举线程会同时调用同一个 `MprpcChannel`；`m_clientFd` 共享、协议是「请求-响应」配对，两个线程会互相读走对方的响应，导致 RPC 挂起。

**处理**：`CallMethod` 内加互斥量串行化；Raft RPC 加 3s 超时兜底。

### 7. 客户端重试饿死选举

**现象**：修完 #6 后仍有 50%+ 的 `ErrWrongLeader`。

**原因**：选举窗口内（约 1s）所有失败请求立刻重试其他节点，2 线程也能打出 2000 QPS，占满 `m_mtx`，选举协程拿不到锁。

**处理**：失败后 2ms 退避；失败率降到 9%，故障窗口 1.2s。

### 8. 端口溢出

**现象**：per-node 模式日志里 `port:-21971`。

**原因**：`bind(port 0)` 返回的是 32768~60999 的临时端口，而 `KvServer`/`RpcProvider` 的 `short` 是有符号 16 位。

**处理**：端口池改为 20000~32000 并逐个 bind 探测。

### 9. 初始化前收到 RPC → 段错误

**现象**：per-node 模式节点启动即 `SIGSEGV`；gdb 栈显示 `___pthread_mutex_lock(mutex=0x0)`。

**原因**：节点 init 时间不同步（`sleep(6) + sleep(N-i)`），先 init 的节点向还没 init 的节点发 `RequestVote`；后者的 `m_persister` 为空，`persist()` 里 `m_persister->SaveRaftState()` 解引用空指针。

**处理**：`m_initialized` 原子标志；三个 RPC handler 在 init 前直接返回。这同时是**单节点重启能工作**的前提。

### 10. availability 口径错误

**现象**：重启 follower 后 `maxGapMs` 变成 11s，判定失败。

**原因**：`fault.inject` 不区分故障类型，重启也被当成「故障开始」。

**处理**：只统计 `kill / stop / partition`；`restart` 不算可用性损失。

## 结论

- 前 5 个问题会让「测试结果不可信」，必须在跑场景前解决；
- 后 5 个是被测系统的真实缺陷，其中 #9 是致命的，#6/#7 会显著放大故障窗口；
- 压测框架的价值不只是出数字，而是把系统在故障下的真实行为暴露出来。
